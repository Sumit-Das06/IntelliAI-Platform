# Milestone 0.5 Review — Engineering Standards (v0.15)

- **Closed:** 2026-07-30
- **Scope shipped:** tooling gate (ruff, mypy strict, pre-commit + gitleaks +
  conventional commits) · GitHub Actions CI (modular, path-filtered, real
  Postgres, `CI OK` aggregation) · platform error contract (nine-type
  taxonomy, one envelope, `Retry-After`, request-ID in every error) · ADRs
  0002–0010 + upgraded template + index · six engineering handbooks.
- **Verification:** 26/26 tests; CI green on clean machines (run #3 after a
  genuine caught failure in run #2); every commit passed the hook gate it
  introduced.

This is an engineering review, not a summary. Answers below are honest.

## 1. What did we build?

The rulebook and the referees. M0 built a working chassis; M0.5 made its
standards self-enforcing: machines reject bad style, types, secrets, big
files, and malformed commits before they land; CI re-proves the
clean-machine promise on every push; every API failure has one permanent
shape; every architectural decision is on the record with review criteria;
and six short handbooks capture only what machines cannot judge.

## 2. Decisions that proved correct during implementation

- **App factory + DI** — every test suite builds isolated apps; zero
  monkeypatching anywhere in 26 tests.
- **uv single lockfile** — CI and Docker reused it verbatim; the Test job's
  env-var-only configuration worked with zero code changes, validating
  12-factor config end-to-end.
- **Modular health checks** — fakes made testing trivial; the protocol
  absorbed the Step-7 engine change without endpoint edits.
- **Fast-hooks-only pre-commit philosophy** — commits stay ~2s; nobody is
  tempted by `--no-verify`.
- **`CI OK` aggregation job** — proved itself on run #2 by correctly going
  red when jobs failed to resolve an action version.
- **Request-ID middleware before error work** — the envelope got
  correlation for free.

## 3. Assumptions not yet validated

- **The entire inference plane is still on paper.** Runtime contract,
  plane separation, CPU latency envelope, provider adapters — no inference
  service exists yet. M2/M3 are the real test of our biggest bets.
- **Tenancy is designed, not exercised** — no auth, no orgs, no cross-org
  test has ever run.
- **Every PRD §10 performance number is unmeasured.**
- **WSL2-for-ML assumption untested** — all Python so far ran fine on
  native Windows; the "WSL2 required" rule hasn't met the workloads it was
  written for (ffmpeg, audio libs) yet.

## 4–6. Technical debt register

| Debt | Intentional? | Resolve by |
|---|---|---|
| Health checkers build clients per call (inflates concurrent latency readings) | ⚠ known, scheduled | M10 observability |
| `BaseHTTPMiddleware` vs raw ASGI | ✅ intentional (readability) | revisit at M8 streaming |

**Blocking M1: none.** Two cheap items (Dependabot, docs-rule amendment)
fold into M1's opening step.

## 7. Abstractions that feel premature

Honest audit: none carry meaningful cost — the "structure now, code when
needed" discipline kept placeholders to READMEs. Two to watch:
- `quota_exceeded_error` exists before any quota system — justified by the
  frozen-type-set rule (adding it later would break SDKs), but it's a type
  with zero raises.
- **The runtime contract risk:** it must be designed against *two* engines
  (whisper AND piper) simultaneously in M2/M3, or it will quietly become
  whisper-shaped. This is the top design risk of the next two milestones.

## 8. Abstractions that will clearly pay off

Org-first tenancy (M1 builds directly on it) · error taxonomy (auth errors
slot into existing types) · naming conventions + migration pipeline (first
real tables inherit everything) · DI aliases (auth adds `CurrentOrg` in one
place) · event logging + request IDs (cross-service tracing arrives free in
M2) · `CI OK` (branch protection requires one check, forever).

## 9. If we started again today

- Authenticate `gh` and create the GitHub repo *before* the first commit
  (identity confusion and blind-CI friction were self-inflicted).
- Enable Dependabot with the first workflow (run #2's failure class would
  be a bot PR instead of a red main).
- Verify action tags exist before pinning (30 seconds vs. a red run).
- Write the dev-environment rule to match reality (native Windows for
  control-plane work; WSL2 when ML deps demand it) instead of aspiration.
- Architecture itself: no regrets yet — but the honest caveat is that
  nothing has met production reality; real regrets surface at M2/M3, and
  this review's successor should re-ask this question then.

## 10. Risks before M1

1. **Auth is hand-rolled and security-critical** — key hashing, timing-safe
   comparison, org scoping. Mitigation: smallest possible scope (API keys
   only; console login deferred), the checklist, and tenancy tests as
   release-blockers.
2. **M1 scope creep** — orgs+users+memberships+keys+auth middleware is the
   largest build yet; step discipline matters more, not less.
3. **Solo bus factor** — every standard lives in repo (mitigated), but
   review is self-review until a second engineer exists.

## 11. Architecture ↔ PRD alignment

Aligned, verified clause-by-clause against PRD §7: stability (envelope +
v1 packages), tenancy (ADR-0010), portability (compose; S3-generic;
frozen-MinIO exit documented), reproducibility (proven by CI on every
push), swappability (contract — pending M2 validation). PRD references to
"forthcoming" ADRs updated to real links this milestone.

## 12. Is the culture actually in the repository?

Evidence for: standards are machines (hooks caught real issues; CI caught a
real failure); honesty is practiced (red run #2 preserved, measurement
artifact documented in M0 review); explain-before-build (11 ADRs, charters
in docstrings); docs-ship-with-code (this review lands in the closing
commit). Evidence against: one written rule (WSL2) didn't match practice —
caught and scheduled for amendment, which is itself the culture working.
Verdict: yes, with the caveat that "review culture" is self-review until
the team grows.
