## 1. Starting state

No iOS project existed. Environment: Windows 11 — no Xcode, no Swift
toolchain, no macOS, no simulator, no iPhone. What that means was
separated honestly from day one: **code + contract verification now;
build/device verification when a Mac is available.** Nothing below
claims Apple-device evidence.

## 2. Architecture (Phase 2)

`apps/keyboard-ios/` — container app + keyboard extension + shared
layer, generated by XcodeGen from a committed `project.yml` (no opaque
pbxproj in review):

- **IntelliAI** (app): onboarding/enablement, API key → shared
  Keychain (masked after save), server address, language +
  contribution settings, the microphone-permission grant (extensions
  cannot present the prompt), the correction editor.
- **IntelliAIKeyboard** (extension, `RequestsOpenAccess`): key rows,
  mic key, language chip, status/error line, dictation state machine,
  insertion via `textDocumentProxy` (native input seam; leading-space
  law mirrored from Android). Cancels recording AND the in-flight
  request when dismissed.
- **Shared/** (compiled into both): `IntelliAIApiClient`,
  `WavRecorder`/`WavEncoder`, `DictationController`, `SettingsStore`
  (App Group), `KeychainStore` (shared access group),
  `DictationLanguage`, `ServerAddress`.

## 3. Public API contract (Phases 3–4) — VERIFIED LIVE

Same endpoint as Web/Android, no iOS-specific route. The exact iOS
request shape (multipart WAV, `X-IntelliAI-Client: ios-keyboard/1.0`,
`model=intelliai-stt`, Auto omitting `language`) ran against the LIVE
production-shaped stack through the Caddy HTTPS edge:

| Arm | Result |
|---|---|
| `language=hi` | 200, served by the promoted E3 route, sample collected |
| `language=en` | 200, incumbent, sample collected |
| Auto (field omitted) | 200, default route, sample collected |
| Correction on a collected sample | 200; original immutable, current updated (DB-verified) |
| DB record | `client_source='ios-keyboard', client_version='1.0'` |

**Backend change (Phase 15), smallest possible and additive**:
`ClientSource.IOS_KEYBOARD = "ios-keyboard"` + one
`ALTER TYPE … ADD VALUE` migration (`a3f8c2d94e61`) + tests (the new
surface records exactly; unknown headers still fall back to `api`; a
mis-typed enum insert is contained by the collection seam — observed
live, transcription unaffected). Nothing else: same gateway, same
runtime, same routing.

## 4. Audio (Phase 5)

AVAudioEngine tap → on-the-fly conversion to 16 kHz/mono/PCM16 →
pure-function RIFF encoder, byte-compatible with Android's. 60 s cap
(cap sends), interruption stop-and-send, audio-session
activate/deactivate, cancellation discards PCM, nothing persisted.

## 5. Security / privacy (Phases 8, 14)

API key: shared **Keychain** only (`AfterFirstUnlock`,
`com.intelliai.keyboard.shared` access group), masked display
(`prefix••••tail`), delete + rotate; never in UserDefaults/files/logs/
clipboard. Non-secret settings: App Group
(`group.com.intelliai.keyboard`) — one source of truth for app and
extension. HTTPS-only in release (validator + ATS); debug may reach
localhost only. Full Access is required for network dictation and is
documented with what it does/does not enable. No claimed guarantee
beyond what the code shows; device-dependent behaviors are flagged.

## 6. Errors (Phase 12)

The envelope contract verbatim from Android: branch on `error.type`
(the 429 quota-vs-rate-limit pair decided by type, never status), one
bounded 503-family retry, product-safe wording table with a leak test
(no qwen/whisper/llama/gguf/artifact strings can appear).

## 7. Tests (Phase 16)

XCTest, pure seams (run on a bare simulator, no entitlements): WAV
header canon · language mapping + Auto omission · multipart formation ·
envelope interpretation (success/sample-id, empty→noSpeech, 429 pair,
missing-vs-bad key, validation message passthrough, unparseable 5xx) ·
server-address law · key masking · settings roundtrips · controller
laws (toggle, duplicate-tap, empty-recording suppression, language
snapshot, cancellation). Runnable on Mac; authored and reviewed now.

## 8. Web/Android regression (Phase 18)

Backend suites green after the additive change (622 api tests incl.
the new client-source cases); Android and Web untouched (no files
changed outside `apps/keyboard-ios/` + the additive backend change).
Production routing unchanged (M26 state); Hostinger untouched.

## 9. What remains for a Mac/iPhone session

`xcodegen generate` → build both targets → run the XCTest bundle →
enable keyboard + Full Access on a device → grant microphone in the
app → dictate Hindi/English → verify insertion, contribution ON/OFF,
correction, bad-key and network-failure paths — the Phase 17 checklist
verbatim. **The microphone-inside-extension restriction is the one
design risk that only a device can settle** (fallback documented in
the README if a target iOS version refuses).
