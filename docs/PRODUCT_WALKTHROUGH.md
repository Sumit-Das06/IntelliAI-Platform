# 1. API Keys

**Console path:** `/console/keys` · **Sidebar:** BUILD → API Keys

## 1.1 The one-sentence idea

An API key is **a password for machines.**

A human signs into the console with a browser. A *program* — the Android
keyboard, a `curl` script, a future mobile or desktop app — cannot do
that. So it presents one long random string instead, and the server uses
it to answer a single question: **which organization is this?**

## 1.2 Anatomy of a key

A real key looks like this (this is the shape, not a live secret):

```
ik_live_ubOPOjSN69AWmN1ue3LY_3q8XumW-CrWcTXlXYVfrmM
└──┬───┘└─────────────────┬──────────────────────┘
namespace          43 random characters
 (8 chars)         = 256 bits of CSPRNG entropy
```

Two parts, two jobs:

- **`ik_live_` — the namespace.** It says at a glance *this is a real
  IntelliAI production key*. Three further namespaces are **reserved but
  deliberately not issuable yet**: `ik_test_` (test-mode keys),
  `ik_service_` (internal service-to-service), `ik_temp_` (short-lived
  delegated keys). Reserving them now means that when test keys arrive,
  no format migration is needed and any external parser written today
  keeps working.
- **The 43 characters — the secret.** Generated by a cryptographic
  random number generator: 256 bits of entropy. Guessing one is not a
  practical attack at any scale.

> Source: `apps/api/src/intelliai_api/core/security.py` — `generate_api_key`,
> `LIVE_NAMESPACE`, `RESERVED_NAMESPACES`.

## 1.3 The most important fact on this page

**The database does not contain your key.** Not encrypted — *absent*.

At creation the server computed a one-way fingerprint and discarded the
original:

```
your key ──HMAC-SHA256, keyed by a server "pepper"──► a1b3f9…  (stored)
```

Exactly three things are persisted:

| Stored | Example | Purpose |
| --- | --- | --- |
| fingerprint (`key_hash`) | `a1b3f9…` (64 hex chars) | the lookup value at authentication time |
| first 16 chars (`key_prefix`) | `ik_live_ubOPOjSN` | display + support ("which key is this?") |
| last 4 chars (`key_last4`) | `hG_w` | display |

That is precisely what the page shows — `ik_live_ubOPOjSN…hG_w`. Nothing
is being withheld by the UI, because **nothing more exists**.

**Why it is built this way.** If an attacker stole the entire database,
they still could not make a single API call: the *pepper* that produces
the fingerprint lives in an environment variable on the server, never in
the database. Two separate security domains — compromising one yields
nothing.

**Consequence:** "shown once" is a hard rule, not UI theatre. There is no
*reveal key* button anywhere, because the server genuinely cannot recover
the secret. Lose it → create a new key and revoke the old one.

> Source: `core/security.py` — `hash_api_key`; `db/models/api_key.py` —
> the stored columns; ADR-0012.

### Why a fast hash and not Argon2/bcrypt?

Password hashing is deliberately *slow* because human-chosen passwords
have low entropy and must resist brute force. An IntelliAI key is 256
bits of machine randomness — brute force is already impossible, so the
slow hash would buy nothing and cost latency on **every single API
request**.

This is written down as a standing invariant: the fast-hash scheme is
valid **only** for platform-generated high-entropy secrets. If
user-chosen credentials ever exist, they take an Argon2id path — never
this one.

## 1.4 The page, column by column

Using the console's own row as the example:

| Column | Example value | What it means |
| --- | --- | --- |
| **Name** | `bootstrap` | A label *you* chose, for humans only. This one is created automatically by `make bootstrap-org`. |
| **This browser** | badge | The key this browser is currently connected with — see §1.7 |
| **Key** | `ik_live_ubOPOjSN…hG_w` | Prefix + last-4. Enough to identify a key on a support call without ever exposing it |
| **Status** | `Active` | Not revoked, not expired |
| **Services** | `IntelliAI STT` | What the platform currently serves. **Honest caveat:** this is *not* a per-key permission — keys are not scoped today; any key can reach any service. Per-key scoping is a future feature |
| **Created** | Aug 3, 2026 | When it was minted |
| **Last used** | Aug 10, 2026 | Last successful authentication (see the throttle in §1.5, step 6) |

## 1.5 What happens on *every* API call

This is the part worth understanding, because the rest of the product
sits on top of it. When the Android keyboard sends a dictation:

```
POST /v1/audio/transcriptions
Authorization: Bearer ik_live_ubOPOjSN...
```

the server runs six steps, and **the order is itself a security
decision**:

1. **Extract the credential from the header.** Absent, or not a `Bearer`
   scheme → `missing_api_key`. Nothing was verified, so nothing was
   rejected — the error says exactly that.
2. **Cheap structural check.** Known namespace? Correct length? Correct
   alphabet? Malformed garbage is refused **before touching the
   database**, so a flood of junk cannot hammer Postgres.
3. **Fingerprint and look up.** One indexed equality query — fast
   precisely because the hash is deterministic.
4. **Constant-time comparison.** Defense in depth: the comparison takes
   the same time whether it matches or not, so an attacker learns
   nothing by measuring response times.
5. **Only now, the state checks.** Revoked → `api_key_revoked`. Expired
   → `api_key_expired`.
   *Why only now?* Those messages help a legitimate owner ("ah, I
   revoked that one"). Telling a **guesser** that a key is revoked would
   confirm the key exists. So the server proves the key is genuine
   first, and only then becomes helpful.
6. **Stamp "last used"** — throttled to at most one write per 60
   seconds, so a busy key does not cause a database write on every
   request. This is why the timestamp is *approximate by design*.

The result is an `AuthContext` carrying the **organization** — which is
how every downstream feature (usage, samples, datasets) knows whose data
this is. The organization and key ids are also bound into the logging
context, so every log line for that request carries them.

> Source: `api/deps.py` — `_extract_bearer_credential`, `current_auth`;
> `services/auth.py` — `authenticate`, `LAST_USED_WRITE_INTERVAL`.

## 1.6 Why keys belong to the organization, not to a person

The console header shows the **organization** ("Sumit Test"), not a user.
That is deliberate.

> A developer leaves the company. If keys belonged to people, deleting
> their account would take production down with them. Instead you revoke
> their **membership** — the servers keep running.

**The trade-off, stated honestly.** Because a key identifies an org
rather than a person, `speech_samples.user_identifier` records the
*acting key*. For the controlled pilot we therefore adopt a convention:
**one key per human**, so that a person's data-deletion request maps
cleanly onto `make erase-user-data --user-identifier key_…`. If a team
shares one key, per-person erasure below key granularity is impossible.

> Source: ADR-0010; [DATA_GOVERNANCE.md](DATA_GOVERNANCE.md);
> [ops/cohort-onboarding.md](ops/cohort-onboarding.md).

## 1.7 The "This browser" badge

Your browser holds one key in local storage. The page compares that
stored key's **first 16 and last 4 characters** against each row; a match
draws the badge. The full secret never travels back from the server — the
browser is simply recognising its own key.

Small feature, real value: when you have five keys and are about to hit
**Revoke**, it answers *"which one am I currently using?"*

> Source: `static/console/keys.html` — `isThisBrowsersKey`.

## 1.8 Create, Revoke, Rotate

**Create** — the server mints a key and returns it. The `key` field of
that one response is **the only place in the entire API surface where a
plaintext key ever appears**. Copy it immediately; it is gone forever
after.

**Revoke** — sets a `revoked_at` timestamp. The row **stays**: soft
revocation, so the audit trail survives and historical usage remains
attributable. The key stops working on its very next request. Revoking
an already-revoked key is harmless and returns it unchanged.

**Rotate (Soon)** — the graceful swap (issue new → both valid briefly →
kill old). **Not built.** Today the manual equivalent is: create a new
key, update your clients, revoke the old one.

> Source: `api/v1/api_keys/routes.py` — `create_api_key`, `list_api_keys`,
> `revoke_api_key`.

## 1.9 How this page connects to everything else

```
API Keys ──► the key pasted into the Android keyboard
         ──► the key the STT Studio uses in your browser
         ──► the key in your curl / Python / JavaScript snippet
                        │
                        ▼
        every request → identifies the ORGANIZATION
                        │
         ┌──────────────┼──────────────┐
         ▼              ▼              ▼
     Usage page   Speech Samples    Datasets
     (metering)   (consent gate)  (training data)
```

The key is the thread running through the whole product. It is how a
dictation spoken into a phone ends up counted on the **Usage** page and
stored under the right tenant on the **Speech Samples** page.

## 1.10 Current limitations (deliberately stated)

| Limitation | Status |
| --- | --- |
| **Revoking the last active key locks the organization out — permanently, with no supported recovery** | ⚠️ **Launch blocker.** Found live on 10 Aug 2026 by revoking the only key of "Sumit Test". Creating a key needs `POST /v1/api-keys`, which needs authentication, which needs a working key; the CLI has no create-key verb (`bootstrap-org` makes a *whole new organization*). The org's samples, datasets, and usage become unreachable. Recovery today requires going **around** the product — calling `IdentityService.issue_api_key()` from a script. **This matters because the pilot issues one key per person and the Revoke button carries no warning.** Proposed fix: a `make create-key org=… name=…` CLI verb (same pattern as `grant-consent`) plus a console guard when revoking the last active key |
| Keys are not scoped per service | By design today; the Services column reflects platform capability, not permission |
| No key rotation | Marked "Soon" in the UI; manual create + revoke works |
| Key stored in browser `localStorage` | Accepted risk for the controlled pilot, documented with mitigations in [SECURITY_GUIDELINES.md](SECURITY_GUIDELINES.md); to be re-decided before any consumer launch |
| Only `ik_live_` is issuable | `ik_test_`, `ik_service_`, `ik_temp_` are reserved format-wise but not implemented |
| The console curl snippet shows the current server | `http://localhost:8000` locally. Release builds of the Android keyboard already refuse non-HTTPS addresses |

# 2. Playground — the STT Studio

**Console path:** `/console/playground` (the old `/playground` still
redirects, so early cohort bookmarks keep working) · **Sidebar:** BUILD →
Playground

## 2.1 The one-sentence idea

The Studio is **the product eating its own dogfood**: a page that speaks
to the exact same public API a customer would call, with nothing
privileged about it.

The page says so itself, above the code samples:

> *"The Studio uses the same public API you would."*

That is not marketing copy — it is literally true, and it is the single
most important thing to understand here. There is no internal endpoint,
no shortcut, no "console mode". When you press **Transcribe**, the
browser sends the same `POST /v1/audio/transcriptions` that the Android
keyboard sends, authenticated with the same kind of key from §1.

**Why this matters for a demo:** whatever you show working in the Studio
is proof that the customer-facing API works.

## 2.2 What is on the screen

Two cards, side by side:

| Left card — **Audio** (input) | Right card — **Transcript** (output) |
| --- | --- |
| Language dropdown | The transcript, in an **editable** textarea |
| 🎤 Record / Upload file | *Save correction* (appears conditionally) |
| Audio player (review before sending) | Summary chips (service, language, duration, time) |
| ☑ Contribute this recording… | ▸ Developer details (request id, sample id, raw JSON) |
| **Transcribe** button | |

Below both: **Use it from code** (cURL / Python / JavaScript) and a
permanent consent notice.

## 2.3 Getting audio in — two doors

**🎤 Record** uses the browser's `MediaRecorder`. It asks for microphone
permission, records until you press Stop, and hands back a blob. The
format is whatever your browser supports best — it tries
`audio/webm;codecs=opus` first, then `audio/webm`, then `audio/mp4`.

**Upload file** takes any `audio/*` file from disk.

Either way the audio lands in the `<audio>` player first, so **you can
listen before you send it**. Only then does the Transcribe button enable.

### An important detail: the format differs from the keyboard

| Client | Sends | Why |
| --- | --- | --- |
| Web Studio | webm/opus (browser's choice) | whatever `MediaRecorder` produces natively |
| Android keyboard | 16 kHz mono PCM16 WAV | what `AudioRecord` captures; no client-side conversion |

**Both are correct, and this is not a fork in the pipeline.** The STT
runtime decodes with ffmpeg, so it accepts many containers. And the
platform stores the **original bytes exactly as received** — never the
converted version — so today's serving choices never fossilise into
tomorrow's training data.

> Source: `static/console/studio.html` — `recorderMime`, `setAudio`;
> `storage/objects.py` — "Original bytes exactly as received".

## 2.4 The Language dropdown

Four options, and one of them behaves differently from the other three:

| You choose | The request contains | Meaning |
| --- | --- | --- |
| **Auto detect** | *no `language` field at all* | the engine detects it |
| English | `language=en` | you are declaring it |
| Hindi (Beta) | `language=hi` | ” |
| Arabic (Beta) | `language=ar` | ” |

Auto is **the absence of a field**, not a value like `"auto"` — the code
is literally `if (langSelect.value) form.append("language", …)`. The
Android keyboard's "Auto" does exactly the same thing. That symmetry is
pinned by a test, so the two clients cannot drift apart.

"(Beta)" mirrors the registry's `available` rung: served honestly,
not yet promised. Since M23/M26, Hindi quality IS measured — the
in-house specialist scores CER 0.11612 on the frozen Hindi benchmark
(-69% relative vs the previous engine); Arabic remains unmeasured on
the incumbent. The label stays until the founder promotes the rung.

## 2.5 The contribution checkbox

> ☑ *Contribute this recording to improve IntelliAI STT (subject to your
> organization's consent)*

Checked by default. Unchecking it adds one header —
`X-IntelliAI-Contribution: off` — and the backend then stores **nothing**
for that request: no audio object, no database row.

Read the label carefully, because the wording is doing real work. It
says *subject to your organization's consent* because this checkbox can
only ever **narrow** collection, never widen it:

```
Is the deployment's collection switch on?   no → nothing stored
        │ yes
Has the ORGANIZATION granted consent?       no → nothing stored   ← the ceiling
        │ yes
Did THIS request opt out?                   yes → nothing stored
        │ no
                                            → Speech Sample stored
```

Ticking the box on an organization that has not granted consent stores
nothing at all. That ordering is deliberate and tested.

## 2.6 What happens when you press Transcribe

Here is the whole journey, in order. This is the same path the keyboard
takes — worth reading once, because everything else in the product hangs
off it.

1. **The browser builds a multipart form:** the audio file,
   `model=intelliai-stt`, `response_format=verbose_json`, and `language`
   *only if* you chose one.
2. **Headers:** `Authorization: Bearer <your key>`,
   `X-IntelliAI-Client: web`, plus the contribution header if you
   unticked the box.
3. **Edge & correlation.** A request id is minted (you will see it in
   Developer details), and an unauthenticated per-IP limit applies before
   any credential is read.
4. **Authentication** — the six steps from §1.5. Result: *which
   organization is this?*
5. **Rate limits** — organization allowance, a per-key subdivision of it,
   and a concurrency slot. Attached to the whole `/v1` router, so no
   endpoint can forget it.
6. **Routing.** The registry maps (public model, language) → a specific
   artifact. Asking a synthesis model to transcribe fails here with
   `capability_mismatch`; an unserved language fails here too — and is
   **recorded as demand** rather than discarded.
7. **Quota check** — plan allowance and spend limit, read from the usage
   ledger. *Before* the expensive work.
8. **The STT runtime transcribes.** It enforces its own limits (25 MiB,
   600 s) and decodes your webm with ffmpeg. This is where the seconds
   go.
9. **The usage ledger is written** — inside the same database
   transaction as the response. This is the permanent commercial fact
   behind the Usage page.
10. **The collection gate runs** (§2.5). Critically: *after* success, and
    **it can never fail your request.** If storage is down, you still get
    your transcript — the customer is never punished for our outage.
11. **The response is sent**, with `X-IntelliAI-Sample` present *only if*
    a sample was actually stored.

Two things worth noticing:

- **Metering is split.** The quota is **read** before the runtime (step
  7); the billable event is **written** after it (step 9). It is two
  things on opposite sides of the work, not one step.
- **Step 10 cannot hurt you.** Collection failure is logged and skipped;
  the customer's 200 stands.

## 2.7 What comes back

The transcript fills the textarea, and the summary chips show
**Service · Language · Audio duration · Time taken**. Because the Studio
asks for `verbose_json`, the response carries the detected language,
duration, and per-segment timings — the keyboard asks for plain `json`
because it only needs the text.

> Same endpoint, same contract, different `response_format`. That is a
> documented API parameter, not a second pipeline.

Note the chip says **"IntelliAI STT"**, never the engine's real name.
That rule is enforced platform-wide and guarded by tests: customers see
the product identity, never the internals.

## 2.8 Developer details — the honesty window

Expand the `▸ Developer details` panel and you get:

| Field | Example | Why it is there |
| --- | --- | --- |
| **Request ID** | `req_15397bf0…` | quote this in a support request; it correlates every log line for that call |
| **Sample ID** | `smp_c53f2dec…` | **the collection decision, made visible** |
| **Client** | `web (X-IntelliAI-Client)` | which client the backend recorded |
| Raw response JSON | the whole body | nothing hidden |

The Sample ID field is the one to demo. It shows one of three things,
and each is a different truth:

| Display | Meaning |
| --- | --- |
| `smp_…` | stored — a Speech Sample now exists |
| `not stored (contribution off)` | *you* opted this request out |
| `not stored (no consent)` | the *organization* has not opted in |

The product distinguishes the two "not stored" reasons instead of
lumping them together, so a tester can tell *whose* decision it was.

## 2.9 The correction flow

**The Save correction button only appears when a sample id came back.**

That is the honest rule: if nothing was stored, there is nothing to
correct, so the product does not offer a button that would quietly do
nothing. (The Android keyboard follows the identical rule with its
"Improve this transcription?" bar.)

When you do correct: edit the textarea, press **Save correction**, and
the browser POSTs `{"corrected_text": "…"}` to
`/v1/audio/transcriptions/{sample_id}/correction`.

Server-side, the crucial part:

```
original_transcript   what the machine said     ← FROZEN, never rewritten
current_transcript    what the human says       ← evolves with each correction
+ a "corrected" event appended to the sample's history
```

### A worked example from the real pilot run

From the local pilot validation (9 Aug 2026), driven in an actual
browser:

```
sample:   smp_c53f2dec3105868a5a896165   (client_source = web, language = en)
original: "Hello intaly AI, this is a voice typing test."     ← unchanged, forever
current:  "Hello IntelliAI, corrected from the web studio."   ← my correction
events:   collected → corrected
```

Both rows still exist in the database. This pairing — *what the machine
heard* against *what a human says it should have been* — is the single
most valuable thing the product collects, and the reason the whole
dataset pipeline exists.

## 2.10 The permanent consent notice

At the bottom of the page, always visible, never dismissible:

> *Recordings, transcripts, and submitted corrections may be stored to
> improve IntelliAI speech models when your organization has granted data
> collection consent. Do not record other people without permission.*

Two deliberate choices. It says **"may be stored … when your organization
has granted consent"** — matching what the code actually does, rather
than the false comfort of "we never use your data". And the second
sentence is an ethical instruction that no code can enforce, so it is
placed where the person holding the microphone will see it.

A test asserts this sentence is present on the page, so it cannot be
quietly deleted in a redesign.

## 2.11 "Use it from code"

Three tabs — cURL, Python, JavaScript — generated live against the server
you are on. This closes the loop with §1: the key you created on the API
Keys page goes straight into these snippets, and the request they make is
byte-for-byte the one the Studio just made.

This is how a pilot customer graduates from *clicking* to *integrating*.

## 2.12 Current limitations

| Limitation | Status |
| --- | --- |
| Hindi and Arabic are labelled "(Beta)" | The registry's `available` rung: served, not promised. Hindi quality is now measured (CER 0.11612 on the frozen Hindi benchmark, M23/M26); Arabic remains unmeasured |
| Recording format depends on the browser | Safari/Firefox may produce different containers. The runtime decodes all of them; the *stored* bytes differ by browser |

| No audio playback of *stored* samples here | That lives on the Speech Samples page (§3) |

# 3. Speech Samples

**Console path:** `/console/samples` · **Sidebar:** DATA → Speech Samples

## 3.1 The one-sentence idea

If the Studio is where speech goes **in**, Speech Samples is where you
see **what the platform actually kept.**

This is the honesty page. Everything the Studio's consent notice
promised — *"recordings, transcripts, and submitted corrections may be
stored"* — is auditable right here. Nothing is stored that you cannot
see, play back, and read.

The subtitle says *"Every consented recording your organization has
contributed."* Note the word **consented**: a row exists here only
because all three gates in §2.5 passed.

## 3.2 What one row shows

```
[Collected] [English] Keyboard  4.4 s  [Corrected ✓]  ▶ Play   Aug 9, 3:42 PM
Hello IntelliAI, corrected from the web studio.
```

| Element | Meaning |
| --- | --- |
| **Status badge** | where the sample sits in its lifecycle (§3.3) |
| **Language** | detected, else requested |
| **Client** | Web / Keyboard / API — the provenance from `X-IntelliAI-Client` |
| **Duration** | seconds of audio |
| **Corrected ✓** | a human has improved this one |
| **▶ Play** | listen to the original recording (§3.7) |
| **The text** | the *current* transcript — the best-known version |

The **Corrected ✓** badge is computed as
`current_transcript !== original_transcript`. The Datasets page defines
"corrected" with the **exact same rule**, so a badge here and a corrected
count there can never disagree.

## 3.3 The status lifecycle

Six statuses exist in the vocabulary:

```
collected → validated → accepted → training → archived
                     ↘ rejected
```

**Honest caveat:** today every sample sits at **`collected`**. There is
no review workflow yet — nothing promotes samples to `validated` or
`accepted`. The vocabulary is defined and the filter offers all six, but
only one is currently reachable.

That is deliberate rather than an oversight: dataset eligibility accepts
anything *not* rejected/archived, precisely so the training pipeline
works before a review workflow exists. When review arrives, the rule
tightens in exactly one place.

## 3.4 Filters and search

Four controls: **search transcripts**, **language**, **status**,
**client**.

The client filter is the one to demo. Switch between **Keyboard** and
**Web** and you see both clients' contributions in one table — the
shared-backend architecture made visible without reading a single log
line.

## 3.5 The detail drawer

Click any row:

```
┌──────────────────────────────────────────┐
│ Sample                     [Collected] ✕ │
│ ▶ ━━━━━━━━━━━━━━━━━━━━ audio player      │
│                                           │
│ Original transcript · immutable           │  ← greyed
│ "Hello intaly AI, this is a voice…"      │
│                                           │
│ Current transcript                        │  ← normal
│ "Hello IntelliAI, corrected from…"       │
│                                           │
│ [chips: language · client · duration…]    │
│                                           │
│ Lifecycle                                 │
│  • Collected   Aug 9, 3:41 PM             │
│  • Corrected   Aug 9, 3:42 PM             │
│                                           │
│ ▸ Developer details                       │
└──────────────────────────────────────────┘
```

**The two transcripts, stacked, with the word "immutable" printed on the
first.** That single design choice teaches the whole data model at a
glance: the machine's output is frozen forever; the human's improvement
lives beside it. Nobody has to be told *we never overwrite what the AI
said* — they can see it.

The **Lifecycle** list is the append-only event history, not a status
field being mutated. Developer details adds the sample id, file size,
consent reference, and timestamps.

## 3.6 Where the data is physically stored

The question everyone asks when they reach this page. **Two stores, on
purpose:**

```
                    ┌──────────────────────────────────────┐
   TRANSCRIPTS  ──► │  PostgreSQL — speech_samples table   │
   (text, metadata) │  container: postgres                 │
                    └──────────────┬───────────────────────┘
                                   │ audio_key (a string pointer)
                                   ▼
                    ┌──────────────────────────────────────┐
   AUDIO BYTES  ──► │  MinIO — bucket "intelliai-audio"    │
   (the recording)  │  container: minio                    │
                    └──────────────────────────────────────┘
```

**Why split?** Databases are poor at large binaries — they bloat backups,
slow queries, and consume memory. Object stores are poor at querying
text. Each holds what it is good at, joined by one string.

### Transcripts → PostgreSQL

Table `speech_samples`, two text columns (`original_transcript`,
`current_transcript`) plus duration, mime type, file size, languages,
client source, `lineage` (which model produced it), `consented_at`, and
`user_identifier`. Lifecycle events live in a second table,
`speech_sample_events`.

### Audio bytes → MinIO

The `audio_key` column is a path string:

```
speech/org_a7b5c3472b231cf8bafa6395/2026/08/smp_2c2c62e2bffcdef0d9809d8a.wav
└──┬──┘└──────────────┬───────────┘ └──┬──┘ └────────────┬─────────────┘└┬┘
capability      organization         year/month        sample id      extension
```

Every part earns its place:

- **`speech/`** — capability prefix, so future sample types (`ocr/`,
  `translation/`) are siblings in the same bucket;
- **`org_…/`** — tenant prefix, so listing or deleting everything for one
  organization is a single prefix operation;
- **`2026/08/`** — month partitioning, so no directory grows unbounded;
- **`smp_….wav`** — the sample's own id, so **row and object are coupled
  by identity, not by lookup**. Given a row you can compute the key;
  given a key you can read the sample id. No index, no join table.

### The bucket has a second prefix

```
intelliai-audio/
├── speech/     ← the recordings          (48 objects, 9.5 MiB)
└── datasets/   ← training manifests      (5 objects, 5.4 KiB)
```

`datasets/` holds the frozen training manifests — text files that
*reference* audio in `speech/` rather than containing any. That ratio
(9.5 MiB against 5.4 KiB) is the design in one number; §4 covers it.

### Physically on disk

Both are Docker volumes:

```
intelliai_pgdata    → /var/lib/docker/volumes/intelliai_pgdata/_data
intelliai_miniodata → /var/lib/docker/volumes/intelliai_miniodata/_data
```

On Windows these live inside the Docker Desktop VM — reach them through
`docker compose exec`, the MinIO console (`localhost:9001`), or Adminer
(`localhost:8081`).

**This is exactly why backup has two halves** (`pg_dump` + `mc mirror`):
lose one and the other is useless — transcripts pointing at missing
audio, or audio nobody can identify.

### What the object contains

**The original bytes, exactly as the device produced them** — visible in
the data itself:

| Client | `mime_type` | Stored as |
| --- | --- | --- |
| Web Studio | `audio/webm;codecs=opus` | `.webm` |
| Android keyboard | `audio/wav` | `.wav` |

The runtime converts for inference, but the conversion is never what gets
stored. Today's engine choices must not fossilise into tomorrow's
training data — switch engines later and the pristine originals are
still there.

### What is deliberately NOT stored

- the API key (only its hash, §1.3);
- audio on the phone (the keyboard holds it in memory only);
- anything typed on the keyboard — only dictated audio;
- non-consented recordings — nothing at all, in either store.

## 3.7 How audio playback works

An HTML `<audio>` tag **cannot send an Authorization header**, so the
page cannot simply point it at the audio URL. Instead:

```
fetch(/v1/speech-samples/{id}/audio, Bearer key)
      → blob → URL.createObjectURL() → <audio src=…>
```

Server side, two decisions matter: the endpoint returns the **original
bytes**, and sets `Cache-Control: private, no-store` — consented voice
data must never linger in a shared cache. A missing object yields a clean
404 `sample_audio_not_found` rather than a broken player.

> Source: `api/v1/speech_samples/routes.py` — `get_speech_sample_audio`;
> `static/console/samples.html` — `audioUrl`.

## 3.8 Tenant isolation, visible

Every query is organization-scoped. Ask for another organization's sample
and the answer is **404, not 403** — deliberately. A 403 would confirm
the sample exists; 404 says *"that does not exist for you"* and leaks
nothing.

## 3.9 Where this sits in the flow

```
Studio / Keyboard  →  consent gates  →  ┌─────────────────┐
                                        │ Speech Samples  │  ← you are here
                                        └────────┬────────┘
                                                 │ eligible ones feed…
                                                 ▼
                                        Datasets → Versions → Training data
```

This is the **inspection window between collection and training**: before
freezing a dataset version, this is where you check what you actually
have.

# 4. Datasets → Versions → Training Data

**Console path:** `/console/datasets` · **Sidebar:** DATA → Datasets

## 4.1 The one-sentence idea

This is where consented samples become **training data you can trust.**

Everything up to now has been alive and moving: new dictations arrive,
corrections change transcripts. You cannot train a model on a moving
target. If someone asks in six months *"what exactly did this model learn
from?"*, you need an exact answer — not "roughly the samples we had in
August".

This page turns a moving pile of recordings into a **frozen, validated,
checksummed artifact**.

## 4.2 Three ideas, and the difference is everything

Think of your recordings as **students in a classroom**:

| Concept | In the classroom | Here | Changes later? |
| --- | --- | --- | --- |
| **Dataset** | a *rule* — "students wearing glasses" | a saved filter | ✅ its matches change as data arrives |
| **Version** | the *photo taken* on 10 August | an immutable snapshot | ❌ never |
| **Preparation** | *checking the photo* is sharp, then framing it | validation + the training file | ❌ once READY |

The classroom keeps changing — students join, leave, get haircuts. **A
photo taken today never changes.** That is the entire point of this page.

The page states it in its own words:

> *"A dataset is a saved definition… Creating a **version** freezes
> exactly which samples match right now."*

## 4.3 A worked example — two rules, one pile of data

A real organization during the walkthrough had exactly **three
recordings**:

| # | From | Length | Corrected? |
| --- | --- | --- | --- |
| 1 | Keyboard | 6.7 s | no |
| 2 | Keyboard | 6.7 s | no |
| 3 | Web | 11.4 s | **yes** ✓ |

Two datasets were created over that same pile:

**"All consented samples"**
```
Recording 1 (keyboard) ✓
Recording 2 (keyboard) ✓
Recording 3 (web)      ✓        → 3 samples, 24.7 s
```

**"Client: Web · Corrected only"**
```
Recording 1 (keyboard) ✗  not web
Recording 2 (keyboard) ✗  not web
Recording 3 (web, corrected) ✓  → 1 sample, 11.4 s
```

Same three recordings. Two rules. Two completely different answers. **A
dataset is nothing more than a rule** — it copies nothing and freezes
nothing.

## 4.4 Why the table shows "—" (the usual confusion)

A brand-new dataset shows dashes in the list, while its drawer shows
real counts:

| NAME | SAMPLES | DURATION | LATEST VERSION |
| --- | --- | --- | --- |
| Test dataset 2 | **—** | **—** | **—** |

…yet the drawer says **Eligible 3**. Not a contradiction — they measure
different things:

- **The drawer** = how many match *right now* (live; grows as you record)
- **The table** = what is in your *frozen snapshot* — and you have not
  taken one yet

The drawer says so explicitly: *"No versions yet — the dataset is only a
definition until you freeze one."* The dashes fill in the moment you
press **Create Version**.

## 4.5 Creating a dataset

**Create Dataset** asks for a name, an optional description, and the
criteria: **language** (All/en/hi/ar), **client** (All/Web/Keyboard/API),
**corrected only**, and a **date range**.

Only the rule is stored. Nothing is copied.

## 4.6 The drawer: "Eligible right now"

Live counts — eligible, duration, corrected, plus breakdowns by language
and client. The note underneath matters:

> *"What a version created this moment would freeze — computed by the
> same rules that create versions."*

**"Computed by the same rules"** is a guarantee, not a claim. There is
literally one eligibility query in the codebase: the preview aggregates
it, and the freeze inserts from it. There is **no second implementation
that could drift**, so the preview can never promise a membership the
freeze does not deliver.

Eligible means: belongs to your organization, not rejected/archived, has
audio (key + bytes + duration), has a non-blank transcript, and carries a
consent snapshot.

## 4.7 Freezing a version

**Create Version** warns you first:

> *"This creates an immutable snapshot of the currently eligible samples.
> Future corrections or new samples will not change this version."*

Server-side, in one transaction:

1. **lock the dataset row** — concurrent freezes serialise instead of
   racing for a version number;
2. **refuse an empty freeze** — a version of nothing is a user error;
3. **one `INSERT…SELECT`** from the eligibility query — the database
   decides the whole set in a single statement;
4. **pin the text** — each member's `current_transcript` is *copied* into
   `training_transcript`;
5. **compute statistics from the membership just inserted** — so stored
   numbers cannot disagree with stored rows;
6. **append `included_in_dataset`** to every member's event history.

**Step 4 is the one to remember.** The version stores a **copy** of the
text, not a reference. That is what makes it immutable.

What is *not* copied: **audio is never duplicated.** Ten versions
containing the same recording still point at one audio object.

## 4.8 Preparing the training data

A frozen version is not yet usable — you do not know whether the audio
still exists or whether a transcript is blank. **Prepare Training Data**
checks.

Preparation reads **only the frozen membership and its pinned
transcripts**. It never re-runs eligibility and never reads
`current_transcript`. That is what makes a version prepared today and
re-prepared in two years resolve to the same examples.

Every member is validated: the audio object exists (a cheap HEAD, not a
download), the pinned transcript is non-blank, a language is known,
duration is positive, and the membership count matches the frozen count.

**The rule that makes this trustworthy: it never silently skips.** 997
valid out of 1,000 is a **FAILED** preparation with machine-readable
reasons — not a quietly smaller artifact. If you are going to train a
model, "1,000 examples" must mean 1,000.

## 4.9 The two outcomes

**✓ Ready** — valid count, duration, language breakdown, and *"Manifest
created … · Ready for future IntelliAI STT fine-tuning."*

**Failed** — valid/invalid counts and *named* reasons: `audio_missing`,
`transcript_missing`, `language_missing`, `duration_invalid`,
`membership_count_mismatch`, `sample_erased`.

The FAILED path is real and was exercised during the pilot: a version was
frozen, its only member erased, and preparation then reported
`membership_count_mismatch` with 0 valid of 1. The system noticed and
refused, loudly.

## 4.10 The artifact itself

Stored at `datasets/{org}/{dataset}/{version}/manifest.jsonl`. A real
one, produced by pressing the buttons on this page:

```jsonl
{"id":"smp_618e…","audio":"speech/org_1f16…/smp_618e….wav","text":"Hello intaly AI, this is a voice typing test.","language":"en","duration_seconds":6.656}
{"id":"smp_d5df…","audio":"speech/org_1f16…/smp_d5df….webm","text":"Hello, my name is Sumit, currently I am 25 years old .","language":"en","duration_seconds":11.4}
{"id":"smp_fa84…","audio":"speech/org_1f16…/smp_fa84….wav","text":"Hello intaly AI, this is a voice typing test.","language":"en","duration_seconds":6.656}
```

Three recordings, three lines. Note line 2 is a `.webm` from the Studio
while the others are `.wav` from the keyboard — **one manifest, both
clients, no distinction made.**

Five fields, deliberately model-agnostic: no engine names, nothing
framework-specific. And **byte-deterministic** — fixed key order, compact
separators, LF endings. Same members → same bytes → same `sha256`. That
is what makes the recorded checksum meaningful: fetch the stored object,
hash it, and it matches (done during both backup drills).

## 4.11 The reproducibility law — proven, not promised

The property worth demonstrating, from the pilot run:

```
1. Freeze v1 → prepare → checksum sha256:6a82b5f1…
2. Correct a member sample AFTER the freeze
3. Re-read v1's preparation → checksum sha256:6a82b5f1…   ← UNCHANGED
   v1's pinned text        → still the pre-correction text ← UNCHANGED
4. Freeze v3 → prepare → different checksum, new text      ← picked up
```

A correction made after freezing **cannot** alter what v1 says. And
`READY` is terminal: pressing Prepare again returns the existing
preparation untouched, so the artifact a future training run cites can
never shift beneath it.

**The one sanctioned exception is erasure.** If a person exercises their
right to be forgotten, the manifest containing their voice is deleted and
the preparation flips to FAILED with reason `sample_erased`. Privacy
outranks reproducibility — but loudly, never silently
([DATA_GOVERNANCE.md](DATA_GOVERNANCE.md)).

## 4.12 Archiving

**Archive** retires a dataset from active work; the modal is explicit
that *"frozen versions remain readable forever."* A soft state, and
idempotent.

## 4.13 Where this leads

```
Speech Samples → Dataset (rule) → Version (frozen) → Preparation (JSONL + checksum)
                                                              │
                                                              ▼
                                                    ╔═══════════════════╗
                                                    ║ FUTURE: fine-tune ║  ← not built
                                                    ╚═══════════════════╝
```

**This is where the product currently stops.** Everything up to the
checksummed artifact exists and is tested. Fine-tuning, evaluation, and
model promotion are the next ML milestone — deliberately not built.

## 4.14 Current limitations

| Limitation | Status |
| --- | --- |
| **A customer cannot download their own manifest** | ⚠️ **Gap found 10 Aug 2026 by using the page.** Preparation reports "✓ Ready" and the manifest genuinely exists in object storage — but there is **no download button and no API route** to fetch it (the dataset router has ten endpoints; none serves the artifact). Only an operator with MinIO credentials can retrieve it. Cause: Commit 12 scoped preparation to *producing* a correct artifact, whose consumer was assumed to be a future training pipeline reading storage directly; nobody asked "what if a human wants it?". Proposed fix: `GET /v1/datasets/{id}/versions/{id}/manifest` — org-scoped, streaming the object exactly as the Speech Samples audio endpoint already does — plus a Download button. **"Ready" that you cannot act on is a broken promise; worth closing before a pilot** |
| No dataset editing | Criteria are fixed at creation — deliberate: editing would silently change what past previews meant |
| No version deletion | Immutable means immutable; archive the dataset instead |
| Preparation is synchronous | Fine at pilot size; large datasets will need a job queue |
| No train/test split | The manifest is one flat list. Holding out an evaluation set belongs to the ML milestone |
| No duplicate detection | The same phrase recorded twice counts twice |
| No cross-organization datasets | Org-scoped by law |

# 5. The Android Keyboard

**Code:** `apps/keyboard-android/` · **Package:** `com.intelliai.keyboard`

## 5.1 The mental shift: it is not an app

Get this first, because everything else follows from it.

You do not *open* the IntelliAI keyboard. You **install** it, and it
becomes the keyboard for **every app on the phone** — WhatsApp, Gmail,
Chrome, banking apps, everything.

Android calls this an `InputMethodService`. It is among the most
privileged things a person can install, because a keyboard by definition
sees every character typed, passwords included.

**That single fact explains every design decision below.** None of it is
paranoia for its own sake; it is the minimum owed to someone who granted
that position.

## 5.2 Setup — four steps, each unavoidable

```
1. Install the APK       → the keyboard exists on the phone
2. Enable IntelliAI      → add it to Android's allowed-keyboards list
3. Select IntelliAI      → make it the active keyboard
4. Paste your API key    → so it can reach your backend
```

Steps 2 and 3 are **separate because Android enforces it**, not by our
choice. Enabling says "this keyboard is permitted"; selecting says "use
it now". Android shows a blunt warning at step 2 ("this keyboard may
collect all the text you type") — that warning is accurate and appears
for every keyboard, Google's included.

The Status card derives its state from the **real system** on every
resume (`InputMethodManager` + `Settings.Secure`), never from a stored
flag, so it is honest the instant you return from Android's settings:

```
✓ IntelliAI Keyboard enabled
✓ IntelliAI Keyboard selected
```

Step 4 is where §1 connects: the key you created on the API Keys page is
pasted here, stored in `EncryptedSharedPreferences` (Android
Keystore-backed), and shown afterwards only as `ik_live_…hG_w`.

## 5.3 The keyboard surface

```
┌─────────────────────────────────┐
│ IntelliAI            [EN]  🎤   │  ← brand bar · language chip · mic
├─────────────────────────────────┤
│  Q W E R T Y U I O P            │
│   A S D F G H J K L             │
│  ⇧  Z X C V B N M  ⌫            │
│ ?123 🌐   IntelliAI   .    ↵     │
└─────────────────────────────────┘
```

An ordinary QWERTY keyboard. The two IntelliAI-specific controls are the
**language chip** and the **microphone**. The brand bar doubles as the
status line — it shows `● Listening`, `Processing…`, and any error.

## 5.4 Dictation

```
Tap 🎤  →  ● Listening  →  Tap ■  →  Processing…  →  text appears
```

1. **Tap the mic.** Checks a key is configured, then requests microphone
   permission if needed.
2. **Recording.** 16 kHz mono PCM16 via `AudioRecord`, accumulated **in
   memory only** — never written to disk.
3. **Tap stop.** The PCM is wrapped as a WAV and posted to
   `/v1/audio/transcriptions`.
4. **Text is inserted** into whatever app you are in, at the cursor, with
   correct joining spaces.

Step 4 is the part that feels magic: the keyboard has no text box of its
own. It types into **WhatsApp's** field through Android's
`InputConnection`. From the app's point of view, you typed it.

Two guardrails: recording **auto-stops at 60 seconds** (and still
transcribes what was said — discarding a minute of speech would be
theft), and anything under **half a second** is treated as a fumbled tap,
never sent, so it cannot cost quota.

## 5.5 Why it can never get stuck

A keyboard frozen on "Processing…" is unusable — you cannot type and you
cannot fix it. So dictation is an explicit state machine:

```
Idle → RequestingPermission → Recording → Processing → Idle
          ↘ denied              ↘ error      ↘ failure
            Idle+message          Idle+msg     Idle+msg
```

**Every path returns to Idle.** There is deliberately no error *state* —
errors are Idle plus one transient human message. Permission denied, no
network, bad key, quota exhausted, server down: each leaves a working
keyboard and an honest sentence.

The machine is pure of Android types — recorder, API, permissions, and
even the clock are injected seams — so every transition including the
60-second auto-stop is unit-tested on the JVM with virtual time.

## 5.6 Language and contribution — captured at the start

Tap the **EN** chip: Auto / English / Hindi / Arabic. Same semantics as
the web — **Auto omits the `language` field entirely**.

The subtle part: language *and* contribution are both **locked at the
moment you tap the mic**. Changing either while recording or uploading
cannot alter the request already in flight; the next one picks up the
change.

That prevents a real bug: speak in English, switch to Hindi mid-upload,
and have the request mislabelled — which would poison the training data
with a wrong language tag.

**Contribution** lives in Settings as *Improve IntelliAI STT* (on by
default). Off sends `X-IntelliAI-Contribution: off`. Same header, same
server-side ceiling as the web checkbox: the organization's consent still
wins.

## 5.7 Correction — and a lesson worth reading

After a dictation that was **actually collected**, a bar appears above
the keys:

```
Improve this transcription?        [Edit]  [Dismiss]
```

Tap **Edit** → the correction editor opens → fix the text → **Save**.

Same honest rule as the web: **the bar appears only when the server
returned a sample id.** No sample → no offer, because there would be
nothing to correct.

One deliberate subtlety: the correction updates the **IntelliAI sample**,
not the text already sitting in WhatsApp. The keyboard does not reach
back into another app's content — it tells the platform "that transcript
was wrong, here is the right text".

### Case study: the bug the emulator could not find

**This is the most instructive failure in the project so far.**

Correction shipped in Commit 13D and was reported VERIFIED through 13E,
the architecture freeze, 14A, 14B, and the full local pilot. Then the
**first real phone** (a Galaxy M15, 10 Aug 2026) broke it within minutes:
the offer bar vanished too quickly, and tapping Edit produced an editor
that **disappeared while the user was typing in it**.

Two causes:

1. **The offer lasted 9 seconds.** Long enough for a script that taps
   instantly; far too short for a human who must read the inserted text,
   judge it wrong, and reach for the button.
2. **The editor was an `AlertDialog` on the IME window carrying
   `FLAG_ALT_FOCUSABLE_IM`.** That flag is correct for the
   `LanguagePicker` — a tap-only list that should suppress the keyboard —
   and exactly wrong for a **text field**: it forbids the window from
   interacting with any input method. On a device that meant: tapping
   the field summoned no keyboard; typing went to the *host app's* field
   instead (the IME was still bound there); that churn fired
   `onFinishInputView`, tearing down the input view; and the dialog —
   attached to that view's window token — was destroyed by the window
   manager mid-edit.

**Why every emulator run passed:** the verification drove the editor with
`adb shell input text`, which injects events *below* the focus layer and
never asks a keyboard to appear. It exercised everything except the thing
that was broken.

**The fix** was a pattern the app already contained. `PermissionActivity`
exists because *an InputMethodService cannot host the runtime-permission
dialog*; the correction editor needed the same treatment for the same
underlying reason — **an IME cannot host its own editable dialog, because
it cannot be its own keyboard client.** `CorrectionActivity` is a real
activity with its own window and focus, which any IME (including
IntelliAI's own) serves normally. Supporting changes: the sample id is
captured *before* launching (taking focus clears `lastCorrection`, so
Save would otherwise silently no-op), the result is a **Toast** rather
than the keyboard's brand bar (the keyboard may not be on screen when the
call returns), and the offer bar now lasts **30 seconds**.

Verified on the device that found it: editor opened, keyboard appeared
and stayed, Save returned 200 in 29 ms, `original_transcript` unchanged,
`current_transcript` updated, lifecycle `collected → corrected`.

**The lesson, stated plainly:** emulator verification is worth a great
deal and it is not a substitute for a physical device. Every report in
this repository labelled "physical device: PENDING" — that label was
load-bearing, and it was right.

> Source: `dictation/CorrectionActivity.kt` (header documents the whole
> failure); commits `1ce5f73`, `a7604f1`.

## 5.8 The privacy rules

Enforced by tests that fail the build, not by good intentions:

| Rule | Enforcement |
| --- | --- |
| **Exactly two permissions** | `RECORD_AUDIO` + `INTERNET`. A test pins the exact set |
| **Audio never touches disk** | A test scans main sources for `FileOutputStream`, `filesDir`, `cacheDir`, `openFileOutput` — any hit is a red build |
| **Nothing is ever logged** | Zero `android.util.Log` calls anywhere. No logging path exists, so keys, text, and audio facts have no route to logcat |
| **Typed text never leaves** | Only dictated audio is transmitted |
| **Key encrypted at rest** | Keystore-backed; displayed only as a prefix+last-4 hint |
| **No analytics / crash / ads SDK** | Firebase, GMS Ads, Amplitude, Mixpanel are classpath-banned by test |
| **No ML-lifecycle code** | The keyboard is a client: no fine-tuning, checkpoints, or model promotion vocabulary |

Verified live on the device: after a full dictation session,
`run-as … find /data/data/com.intelliai.keyboard` returned **no audio
files**, and `logcat` contained **no API key**.

## 5.9 Debug vs release

| | Debug | Release |
| --- | --- | --- |
| Default server | `http://10.0.2.2:8000` | *empty* — a deliberate configuration |
| Cleartext | allowed, to three dev hosts only | **refused** |
| `localhost` / `127.0.0.1` / `10.0.2.2` | permitted | **refused even over HTTPS** |

Release refuses a development address in three independent places: the
settings screen (at entry), the API client (before any request leaves the
device, with an honest `HTTPS_REQUIRED` error), and Android's own
network-security default. Proven on-device: the release build read a
leftover `http://10.0.2.2:8000` setting and refused it rather than
failing opaquely.

Sizes: **debug ≈ 7.5 MB**, **release ≈ 6.0 MB** (unsigned — no
production signing key exists, deliberately).

## 5.10 Testing against the local stack from a real phone

The emulator reaches the host at `10.0.2.2`. A physical phone has no such
address, and the API deliberately binds `127.0.0.1` only (nothing should
face the LAN). The bridge is USB:

```bash
adb reverse tcp:8000 tcp:8000     # phone's own localhost:8000 → laptop
adb install -r app/build/outputs/apk/debug/app-debug.apk
# then in the app: API Server = http://localhost:8000
```

`adb reverse` keeps the safe loopback binding intact — nothing is exposed
to Wi-Fi. **Re-run it after any unplug, reboot, or laptop sleep**; a
dropped tunnel is the single most common cause of "it stopped working".

## 5.11 Same backend — the proof

The architectural claim, as data. From the database after driving both
clients:

```
client_source | client_version | samples
--------------+----------------+--------
 keyboard     | 1.0            |   24
 web          |                |   12
```

Same table, same columns, same pipeline, same model. The **only**
difference is the `X-IntelliAI-Client` header. There is no Android
endpoint, no Android STT service, no Android database.

`WebKeyboardContractTest` pins it: same endpoint, same model id, same
auth, same language semantics, same error envelope, same correction
endpoint, same collection signal. Fork the pipeline and the build goes
red.

| Every user needs an API key | Coherent for an enterprise pilot; not a consumer product shape (see [milestones/13.5](milestones/13.5-architecture-freeze-review.md)) |
| No streaming dictation | One recording, one request, one response |
| Arabic sets the dictation language only | The typing layout stays QWERTY — no Arabic script keyboard |
